# 段階A：実行可能性・構成案・費用・未決事項

作成日：2026-09-22 ／ 対象：AI収益化・自動化管理アプリ 要件定義書（2026-09-22版）

> **本書の読み方**
> - **[確定]** 要件定義書に明記された条件、または公式資料で確認した事実
> - **[提案]** こちらからの提案。**承認前は確定ではない**

## 1. 要件理解（確認）

要件定義書を以下のように理解した。相違があれば指摘してほしい。

| 項目 | 理解 |
|---|---|
| 目的 | 複数の収益事業をAIと自動処理で運用。利用者は確認・承認・例外判断のみ |
| 目標 | 当面 月5万円、将来 月10万円以上（税引前の運用利益。**達成・時期は保証しない**） |
| 費用 | 初期の追加支出ゼロ。有料化は事前承認制 |
| 実行環境 | MacBook Pro 13"（平日9-21時は会社業務。常時起動を前提にしない）＋ スマホから遠隔操作 |
| 最重要原則 | **一律固定をしない。** 事業・アカウント・機能ごとに最適な実行方式を選ぶ |
| 投稿上限 | 各アカウント原則1日1本。品質不合格なら投稿しない |

### 1.1 特に重く受け止めた指示

- 「全機能をローカル、クラウド、単一AI、毎回承認などに一律固定しない」
- 「実績とサンプル、未接続と取得済み、承認済みと実行完了を明確に区別する」
- 「見た目だけの画面を、連携済み・運用可能と報告しない」
- 「実行できていない受入条件を『完了』にしない」

## 4. 構成案 [提案]

要件定義書§4の責務分担に沿う。**一律にしない**という原則に従い、機能ごとに実行先を変える。

```
┌─ スマホ／PC ブラウザ ─────────────────────────┐
│  ログイン → ホーム／事業／承認／予定／分析          │
└───────────────┬───────────────────────────┘
                │ HTTPS
┌───────────────▼───────────────────────────┐
│  Web側（常時稼働・Fly.io等）                       │
│   認証 / 管理画面 / 設定 / 承認 / ジョブ台帳 /       │
│   最終同期データ / 監査ログ / 軽量な外部API呼び出し   │
│   DB: PostgreSQL（Neon）                          │
└───────────────┬───────────────────────────┘
                │ Macから外向きにポーリング（公開ポートを開けない）
┌───────────────▼───────────────────────────┐
│  Macワーカー（不定期稼働）                          │
│   動画合成(ffmpeg) / 音量調整 / 変換 /              │
│   ローカルAI（SDXL等） / 重い処理                    │
│   ※ 業務時間・バッテリー・空き容量で自動退避          │
└───────────────────────────────────────────┘
                │
        外部サービス（YouTube API / Threads API / Gemini / Cloudflare …）
```

### 4.1 「一律にしない」の具体化 [提案]

| 機能 | 実行先 | 理由 |
|---|---|---|
| 文章生成 | Web側 → Gemini API | 軽量。Macの起動に依存させない |
| 画像生成（品質重視） | Macワーカー → ローカルSDXL | 無料・無制限・商用可 |
| 画像生成（Mac停止中） | Web側 → Cloudflare 無料枠 | Mac依存を断つための代替経路 |
| 動画合成 | Macワーカー（ffmpeg） | クラウド無料枠では処理量・保存量が足りない |
| 投稿（YouTube/Threads） | Web側 | 常時稼働が必要。Mac停止中でも予約実行できる |
| 投稿（X/note） | 本人操作 | API無料枠なし／APIなし。完成素材と手順を渡す |
| 検査（規約・重複・品質） | Web側（通常プログラム＋一部AI） | AIが不要な判定はプログラムで処理（要件F02） |

### 4.2 保存方針 [提案]

| 種類 | 保存先 | 理由 |
|---|---|---|
| 設定・承認・ジョブ・収益記録 | Web側DB（日次バックアップ） | 遠隔から必ず見える必要がある |
| 動画・音源の**原本** | Mac + 外部ストレージ | クラウド無料枠に収まらない |
| 遠隔確認用**プレビュー**（低解像度・短尺） | Web側 | 署名付き期限URL。無条件の公開URLにしない |

## 5. UI方針 [提案]

既存の承認UIは**設計は流用、実装は作り直し**とする。

- 流用する設計判断：スマホ幅前提、下タブ（ホーム／事業／承認／予定／分析）、
  リスクに応じた承認の出し分け、状態を色だけに依存させない表示、
  「上書き承認」を最も目立たない位置に置く
- 作り直す理由：新要件では認証・事業/アカウントの多階層・遠隔プレビュー・
  PC待ち状態の表示が加わり、データモデルが変わる

**操作可能な画面案（ホーム／承認／事業設定）は次に提出する。** 本書では方針のみ。

## 10. 無料条件に収まるかの見積もり [提案]

| 項目 | 月額 | 根拠 |
|---|---|---|
| 文章生成（Gemini 無料枠） | 0円 | 1,500回/日。1日30件生成でも十分 |
| 画像生成（ローカルSDXL） | 0円 | 電気代のみ。U1 次第 |
| 画像生成（Cloudflare 無料枠） | 0円 | 日次上限あり。Mac停止時の代替 |
| Web側ホスティング | 0円 | Fly.io または Oracle Always Free（U3） |
| DB | 0円 | Neon 無料枠 |
| YouTube / Threads API | 0円 | 無料 |
| **合計** | **0円** | |

### 避けられない制約 [確定]

1. **完全な無人化はできない。** Adobe Stock と note は自動提出・自動投稿が認められていない。
   X は有料。本人操作が残る範囲を、アプリ上で正確に表示する設計とする。
2. **「無料・24時間・無制限保存」は同時に成立しない。** 動画原本はクラウド無料枠に収まらないため、
   原本はMac＋外部ストレージ、遠隔確認はプレビューのみとする。
3. **Mac停止中は重い制作が止まる。** 文章生成と投稿はWeb側に置くことで影響を限定するが、
   動画合成とローカル画像生成は止まる。「PC待ち」として表示する。
4. **審査待ちの期間がある。** Threads は約1週間、TikTok は2〜6週間。
   この間はその媒体の自動投稿ができない。
