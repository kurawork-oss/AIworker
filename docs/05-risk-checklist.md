# 5. リスクヘッジ チェックリスト

`aiworker checklist` で表示できます。
**A〜C は運用開始前に必須**、D以降は定期確認です。

---

## A. 運用開始前（1回だけ・全項目必須）

### A-1. 停止できることの確認 ← 最優先

停止できないシステムを動かしてはいけません。生成より先にこれを確認します。

- [ ] `aiworker stop --reason "テスト"` を実行し、`aiworker status` に停止が表示される
- [ ] 停止中に `aiworker publish` を実行して、何も公開されないことを確認した
- [ ] `aiworker resume --yes` で解除できた
- [ ] `touch var/STOP` だけでも停止することを確認した（DBが壊れていても止められる経路）
- [ ] `rm var/STOP` で解除できた
- [ ] **緊急停止コマンドをスマホのメモ等、PCを開かずに見られる場所に保存した**

### A-2. アラートが実際に届くことの確認

- [ ] `.env` に `DISCORD_WEBHOOK_URL` または `SLACK_WEBHOOK_URL` を設定した
- [ ] `config.yaml` の `notify.channels` に `discord` / `slack` を追加した
- [ ] `aiworker report --notify` を実行し、**実際にスマホに通知が届いた**
- [ ] `aiworker doctor` が通知設定について警告を出していない
- [ ] 通知先が、自分が1日1回は必ず見る場所である

> console のみの設定は「誰も見ていない端末のターミナルに出力する」ことと同義です。

### A-3. 規約の確認（プラットフォームごと）

有効化する**各**プラットフォームについて：

- [ ] 最新の利用規約・コミュニティガイドラインに目を通した（確認日を記録）
- [ ] 自動投稿・API利用が許可されているか確認した
- [ ] AI生成コンテンツの開示義務の有無を確認した
- [ ] アフィリエイトリンクの掲載可否と表記要件を確認した
- [ ] 1日あたりの投稿数の目安・制限を確認した
- [ ] **正規APIがない経路を自動投稿しようとしていない**（note等）

確認記録の例：

| プラットフォーム | 確認日 | 自動投稿 | AI開示 | アフィリエイト | 日次目安 |
|---|---|---|---|---|---|
| X | | | | | |
| Threads | | | | | |
| note | | 不可 | | | |
| YouTube | | | 必要 | | |
| Adobe Stock | | | 必要 | | |

### A-4. 設定の妥当性

- [ ] `aiworker doctor` が `✗`（エラー）を出していない
- [ ] `dry_run: true` のまま開始する
- [ ] 全プラットフォームの `publisher` が `manual` または `dryrun`
- [ ] `daily_limit` が控えめ（X/Threads 5件以下、YouTube 1〜3件、note 1件）
- [ ] `min_interval_minutes` が60以上
- [ ] `active_hours` が自分の生活時間帯と矛盾しない
- [ ] `require_human_approval: true`（変更不可だが目視確認）
- [ ] `generation.max_pending_per_channel` が自分が1日で捌ける件数の2〜3倍以内

### A-5. 秘密情報の取り扱い

- [ ] `.env` がリポジトリにコミットされていない（`git status` で確認）
- [ ] `chmod 600 .env` を実行した
- [ ] `config/config.yaml` に生のAPIキーが書かれていない（`${ENV:...}` 参照のみ）
- [ ] `config/policy/*.yaml`（実ファイル）がコミットされていない
- [ ] `git log -p | grep -i -E "api[_-]?key|secret|token"` で過去のコミットにも鍵がない

### A-6. 禁止リストの整備

- [ ] `config/policy/banned_terms.yaml` を作成した（example をコピー）
- [ ] 自分のジャンルで危険な語を追加した
- [ ] 取引先名・クライアント名を `real_person_terms` / `trademark_terms` に追加した
- [ ] 以下でブロックされることを実際に確認した：
  - [ ] 「絶対に稼げる」等の収益保証表現
  - [ ] PR表記のないアフィリエイトリンク
  - [ ] 「〇〇風」等の作風模倣プロンプト

### A-7. 収益源の分散

- [ ] **3つ以上**の収益源を並行運用する計画がある
- [ ] 1つが停止しても他が影響を受けない（別アカウント・別API・別入金経路）
- [ ] 各プラットフォームのアカウントで**同じパスワードを使い回していない**
- [ ] 主要アカウントで2要素認証を有効にした
- [ ] 収益の70%以上が1ソースに集中していない（`aiworker report` が警告する）

### A-8. バックアップ

- [ ] `var/aiworker.db` の日次バックアップを設定した
- [ ] バックアップからの復元を1回試した
- [ ] `.env` を別の安全な場所（パスワードマネージャ等）に保管した

---

## B. 初回の生成・承認サイクル（dry-run のまま）

- [ ] `aiworker generate --channel social_post --count 3` が成功した
- [ ] `aiworker review list --verbose` で内容と判定理由が読めた
- [ ] 生成物を**全文**読んだ。事実誤認・不自然な表現・自分の名前で出せない内容がない
- [ ] 1件をわざと却下し、`aiworker plan` の対象から外れることを確認した
- [ ] 1件を承認 → `plan` → `publish` まで通し、公開時刻が分散していることを確認した
- [ ] `var/outbox/` に出力された下書きを確認した
- [ ] `aiworker report` に結果が反映されている

### 生成物の品質確認（人間にしかできない部分）

- [ ] 事実として書かれている内容に、確認できない数字や出典のない統計がない
- [ ] 自分の実体験でないことを実体験のように書いていない
- [ ] 同じテーマの過去投稿と、**切り口が実際に違う**
- [ ] 誰かを傷つけたり誤解させたりする表現がない
- [ ] 自分の名前で出して恥ずかしくない

---

## C. 本番移行（1プラットフォームずつ）

**全プラットフォームを同時に本番化しないでください。**

- [ ] A・Bの全項目が完了している
- [ ] 最初の1つだけを選んだ（推奨：最も失っても痛くないアカウント）
- [ ] そのプラットフォームの規約確認（A-3）が済んでいる
- [ ] 2週間は `publisher: manual` で運用し、生成物の品質が安定していることを確認した
- [ ] 手動投稿した分を毎回 `aiworker mark-published` で記録した
- [ ] 異常なし（リーチ急減なし・警告なし）を確認した
- [ ] （API自動投稿に移行する場合）正規APIで、規約上許可されていることを再確認した
- [ ] 移行後最初の1週間は毎日 `aiworker status` を確認する

---

## D. 毎日（3分）

- [ ] `aiworker status` — 停止中の系統がないか
- [ ] `aiworker review list` — 承認待ちを処理（ブロック分は理由を読む）
- [ ] 各プラットフォームの通知欄を目視（警告メッセージが来ていないか）
- [ ] アラートが届いていた場合、原因を確認するまで再開しない

## E. 毎週（15分）

- [ ] `aiworker report --days 7` を読む
- [ ] リーチ・エンゲージメントの推移を確認（`aiworker metrics add` で記録）
- [ ] 収益CSVを取り込む（`aiworker revenue import`）
- [ ] 収益の集中度を確認（1ソース70%超の警告が出ていないか）
- [ ] 生成物をランダムに3件全文読む（自動チェックをすり抜けた劣化の発見）
- [ ] 承認率が極端に高い（95%超）場合、**自分がゴム印になっていないか**を疑う
- [ ] 失敗ジョブの原因を確認した

## F. 毎月（30分）

- [ ] 各プラットフォームの規約更新を確認（A-3の表を更新）
- [ ] 上限値が実態に合っているか見直す（**上げるのは慎重に、下げるのは即座に**）
- [ ] 禁止リストに新しい語を追加
- [ ] `var/aiworker.db` のバックアップから復元できることを確認
- [ ] `aiworker prune` でログを整理
- [ ] 過去1ヶ月の `approve_override` を全件レビュー
      （`aiworker events --category approval`。上書きが常態化していたらルールの方を直す）
- [ ] 収益源が3つ以上維持されているか

---

## G. 異常時の対応手順

### アカウント警告・投稿非表示・リーチ急減を検知したら

1. **まず止める**：`aiworker stop --platform <名前> --reason "警告検知"`
   （判断は後でよい。止めるのは即座に）
2. 該当プラットフォームの通知欄・メールを確認
3. 直近1週間の投稿を読み返し、規約に触れそうなものを特定
4. 該当する投稿を削除または修正
5. 原因が特定でき、対策を設定に反映するまで**再開しない**
6. 再開は `aiworker resume --platform <名前> --yes`
7. 再開後1週間は投稿数を半分にして様子を見る

### 連続投稿失敗で自動停止したら

1. `aiworker events --level error` でエラー内容を確認
2. 認証エラー → 鍵の再発行。規約エラー → **内容の問題なので再開しない**
3. 一時的なAPI障害と確認できた場合のみ再開

### 誤って不適切な内容を公開してしまったら

1. `aiworker stop --reason "誤公開"`（全停止）
2. 該当投稿を削除
3. `aiworker events` で、なぜガードレールを通過したかを確認
4. **禁止リストまたはルールを更新**（同じものが二度通らないようにする）
5. 対策を入れてから再開

## H. やってはいけないこと

- [ ] `require_human_approval` を無効化しようとする（設定エラーになります）
- [ ] 承認せずにDBを直接操作して公開する
- [ ] `--force` を確認せず常用する（上書きが常態化したら承認ゲートは機能していません）
- [ ] 全プラットフォームを同時に本番化する
- [ ] 上限を「調子がいいから」と一気に引き上げる
- [ ] 正規APIのないプラットフォームを自動投稿する
- [ ] アラート先を設定せずに無人運用する
- [ ] 生成物を読まずに一括承認する
- [ ] 同じテンプレートを別アカウントで使い回す
- [ ] `.env` をコミットする
