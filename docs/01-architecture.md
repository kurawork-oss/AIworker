# 1. システムアーキテクチャ

## 1.1 設計の中心にある1つの原則

> **承認されていないコンテンツは、どの経路からも外部に出ない。**

この1文がアーキテクチャのほぼ全てを決めています。

- 生成エンジンは `approved` 状態を**書き込めない**（`pending_review` か `blocked` のみ）
- 承認は `approval/service.py` だけが行い、必ず `approvals` テーブルに actor 付きで残る
- 公開直前に**もう一度**全チェックをやり直す（承認後に状況が変わっている可能性があるため）

「人間が最低限の確認だけで安全に運用できる」ための設計は、人間の作業を減らすことではなく、
**人間が見落としても事故にならない範囲を広げること**で実現しています。

## 1.3 コンテンツの状態遷移

状態遷移図がそのまま安全性の仕様になっています。
`approved` に入る矢印が1本しかないことが重要です。

```
                       [生成]
                          │
            ガードレール自動判定（policy + quality）
                    ┌─────┴─────┐
                 合格│           │不合格
                    ▼           ▼
            pending_review   blocked
                    │           │
                    │           │ 人間が --force + 理由 を明示
        ┌───────────┼───────────┤  （approve_override として監査記録）
        │           │           │
   修正依頼│      却下 │      承認 │
        ▼           ▼           ▼
  needs_revision  rejected   approved  ←──── ここに入る矢印は「人間の承認」だけ
        │                        │
        │ 編集 → 再チェック         │ aiworker plan（枠の割当）
        └────→ pending_review     ▼
                              scheduled
                                  │
                        aiworker publish
                                  │
                    公開直前の再チェック（_preflight）
                    ┌─────────────┼─────────────┐
                 却下│          延期│          合格│
         （要人間判断）│  （枠の都合） │             │
                    ▼             ▼             ▼
                 blocked      scheduled      published
                                （時刻のみ変更）    │
                                              失敗時
                                                ▼
                                             failed → 連続でkillswitch
```

**編集は承認を引き継ぎません。** 承認済みの本文を編集すると `pending_review` に戻ります。
「承認した内容」と「公開される内容」が一致することを保証するためです。

## 1.4 公開直前チェック（_preflight）の中身

`scheduler/planner.py` が公開の直前に毎回実行します。予約時点の判断は**ヒントであって許可ではない**、
という考え方です。

| # | 検査 | 失敗時の扱い | 理由 |
|---|------|-------------|------|
| 1 | コンテンツが存在するか | block | 削除済みを公開しない |
| 2 | 状態が approved/scheduled か | block | 予約後に却下されたものを止める |
| 3 | 承認記録(actor, 時刻)があるか | block | DB直接操作での迂回を防ぐ |
| 4 | policy が blocking でないか（override記録がある場合を除く） | block | 承認後に規約が変わった場合に対応 |
| 5 | killswitch（全体/プラットフォーム別） | **defer** | 停止中は「失敗」ではなく「待機」 |
| 6 | プラットフォームが有効か | defer | 設定変更に追従 |
| 7 | 日次/週次上限・最小間隔・活動時間帯 | **defer** | 枠がないだけ。次の枠に再配置 |

**block と defer を分けているのが要点です。**
「今は投稿枠がない」は正常動作なので、連続失敗カウンタを進めてはいけません。
これを混同すると、レートリミットが正しく働いているのに緊急停止が誤発火します。

## 1.5 データフロー（1日の典型例）

```
06:00  cron → aiworker generate --channel social_post --count 3
                └ 多様性制御で theme×angle×tone を選択（直近の組合せは除外）
                └ LLM生成 → policy/quality 判定 → pending_review で保存
                └ キューが満杯(既定30件)なら生成しない ← 背圧制御

08:00  人間 → aiworker review list（または Web UI をスマホで開く）
                └ 3分で承認/却下/修正依頼。ブロック分は理由が表示される

08:05  cron → aiworker plan
                └ 承認済みに投稿枠を割当。時刻はランダム分散
                └ 既に予約済みの枠も上限計算に含める（二重予約の防止）

毎時   cron → aiworker publish
                └ 枠が来たジョブだけ実行。直前に全再チェック
                └ publisher: manual なら var/outbox/ に下書きを出力
                └ 失敗 → リトライ（TransientErrorのみ）→ 連続失敗で自動停止
                └ 実行後に異常検知スキャン

20:00  cron → aiworker report --notify
                └ 承認待ち/上限消化/エラー/収益/次のアクションを1画面で通知
```

## 1.6 技術選定の理由

| 領域 | 採用 | 理由 |
|------|------|------|
| 言語 | Python 3.11 + 標準ライブラリ + PyYAML | 追加依存ほぼゼロ。無料VPSでも動く |
| 永続化 | SQLite 1ファイル | トランザクションがある。`approved` と `published` の不整合を防げる。バックアップは `cp` 1回 |
| 設定 | YAML（挙動） + .env（秘密情報） | `grep -r` で鍵が出てこない構造にする |
| LLM | 抽象化して mock / claude_cli / anthropic | 既定を mock にして、鍵なし・課金なしで全経路をテストできる |
| 通知 | urllib で Webhook POST | SDK不要。通知の失敗が本体を落とさないよう全て握り潰してboolで返す |
| 承認UI | CLI（必須） + FastAPI（任意） | CLIだけで完結。UIは「スマホで3分」のためのおまけ |
| ワークフロー | cron または n8n セルフホスト | どちらでも同じCLIを叩くだけ。n8nは必須ではない |
| 公開 | 既定は manual（下書き出力） | 後述 |

## 1.7 「自動投稿」をあえて既定にしていない理由

要件では「ほぼ自動」が目標ですが、初期設定の `publisher` は `manual`（`var/outbox/` に
貼り付け用ファイルを出力）にしてあります。理由は3つです。

1. **正規APIが存在しない経路がある。** note には公開されている投稿APIがありません。
   非公式な自動化はほぼ確実に利用規約違反で、アカウント停止リスクが最も高い部分です。
   これは本システムが避けようとしているリスクそのものです。
2. **APIがある経路も、利用条件の確認が先。** X / Threads / YouTube には正規APIがありますが、
   利用枠・自動投稿の可否・開示義務は変わります。`publishers/registry.py:ADAPTERS` に
   明示的に登録されたアダプタだけが到達可能な設計で、「ファイルを置いたら有効になる」ことはありません。
3. **manual でも自動化の価値はほぼ全部残る。** 生成・多様性確保・規約チェック・重複検知・
   上限管理・時刻分散・記録・収益集計は全部自動です。人間に残るのは「貼って投稿する」だけで、
   ここが最もアカウントを守ります。

自動投稿に移行する場合は、**1つのプラットフォームだけ**を `dry_run: false` + 実アダプタにして、
2週間程度観察してから次に進んでください。手順は `docs/04-mvp-setup.md` の最後にあります。
