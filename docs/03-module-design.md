# 3. 各モジュールの詳細設計

各モジュールについて「責務 / 主要API / 設計判断 / 拡張方法」を記載します。

---

## 3.1 core/config.py — 設定

**責務**: YAML（挙動）と環境変数（秘密情報）を読み、検証済みの `Settings` を返す。

**主要API**
```python
load_settings(path=None) -> Settings     # 読込 + 検証。失敗時は ConfigError
Settings.platform(name) -> PlatformConfig
Settings.validate()                      # 起動時に必ず実行される
```

**設計判断**

- **秘密情報はYAMLに書けない。** YAML中の `${ENV:VAR_NAME}` だけが環境変数を参照する唯一の手段で、
  読込時に解決されます。設定ファイルをそのままリポジトリに置いても鍵が漏れません。
- **`require_human_approval: false` は設定エラーになる。** 「あとで一時的にオフにする」が
  恒久化するのを防ぐため、設定では無効化できないようにしてあります。
  無人公開が必要なら、それはこのシステムの用途ではありません。
- **未知のキーはエラー。** `dailylimit`（アンダースコア忘れ）のようなタイプミスが
  「上限未設定」として黙って通ると事故になるため、知らないキーは起動時に落とします。
- **禁止リストは別ファイル。** `config/policy/*.yaml` を読み込んでマージします。
  実ファイルは gitignore されているので、取引先名など公開したくない語を安全に足せます。

**検証している内容**: `daily_limit <= weekly_limit` / `0 <= 開始 < 終了 <= 24` /
`require_ai_disclosure` なら `disclosure_text` 必須 / `max_similarity` が (0,1] など。

## 3.2 core/db.py — 永続化

**責務**: SQLite のスキーマと全クエリ。

**テーブル**

| テーブル | 役割 | 要点 |
|---------|------|------|
| `content_items` | コンテンツ本体と判定結果 | 判定根拠(`policy_report`/`quality_report`)を一緒に保存し、レビュー時に理由が見える |
| `publish_jobs` | 投稿ジョブ | `content_id` に**部分ユニークインデックス**。open状態のジョブは1件のみ＝二重投稿の構造的防止 |
| `approvals` | 承認の監査証跡 | 誰がいつ何をしたか。override は `approve_override` として別アクション |
| `events` | 運用ログ | 30日で `prune`。アラート判定もここを読む |
| `metrics` | リーチ・表示回数 | リーチ急減検知の入力 |
| `revenue` | 収益 | `(date, source, account, note)` でユニーク＝CSV再取込しても二重計上しない |
| `kv` | killswitch フラグ等 | |

**設計判断**

- **`isolation_level=None` + 明示的な `BEGIN IMMEDIATE`。** Python の暗黙トランザクションを切り、
  `db.transaction()` で囲んだ範囲だけが原子的になるようにしています。
  「承認は書けたがジョブのキャンセルは書けなかった」という中途半端な状態を作らないためです。
- **WAL モード + `busy_timeout=30s`。** cron と Web UI が同時に触っても壊れません。
- **`update_job` はカラム名をホワイトリスト検証。** 呼び出し側のタイプミスで
  無言の no-op になるのを防ぎます。
- **外部キー ON。** 削除済みコンテンツを指すジョブは作れません。

## 3.3 guard/killswitch.py — 緊急停止

**責務**: 全体/プラットフォーム単位の即時停止。

```python
check(conn, state_dir, platform=None) -> HaltState   # 公開前に毎回呼ばれる
engage(conn, state_dir, reason=, actor=, platform=None)
release(conn, state_dir, actor=, platform=None)
active_halts(conn, state_dir) -> list[HaltState]
```

**設計判断**

- **二重化。** DBのフラグと `var/STOP` ファイルの両方を見ます。どちらか一方でも停止です。
  DBがロックされていても壊れていても `touch var/STOP` で止まる、という点が重要で、
  緊急停止が一番必要な状況ほど他のものが壊れているからです。
- **自動解除はしない。** 異常検知は自動で停止できますが、解除は必ず人間の操作
  （`aiworker resume --yes`）です。`--yes` なしでは停止理由を表示して終了します。
- **全体停止はプラットフォーム別停止に優先。** 判定順が固定なので、
  「全体停止中なのに一部が動く」状態が起きません。

## 3.4 guard/quota.py — 上限とリズム

**責務**: 「いつ・何件まで投稿してよいか」の唯一の判断者。

```python
state(conn, settings, platform, account) -> QuotaState       # 消化状況
check_slot(conn, settings, platform, account, when) -> (bool, str)
next_slot(conn, settings, platform, account, after=) -> datetime | None
```

**3つの制限を同時に課しています。** それぞれ別の「BANされ方」に対応しているためです。

| 制限 | 対応するリスク |
|------|--------------|
| 日次 / 週次上限 | 総量。単純な投稿しすぎ |
| 最小投稿間隔 | バースト性。10分で10投稿は総量が少なくてもbotに見える |
| 活動時間帯 | 生活リズム。毎晩4時に投稿する人間はいない |

**設計判断**

- **予約済みの未来の枠も消化としてカウント。** `plan` を2回実行しても同じ日に
  二重予約されません。これを忘れると上限が実質無効になります。
- **`exclude_job_id`。** 公開直前のチェックでは、そのジョブ自身の予約を除外します。
  除外しないと全てのジョブが「自分自身と近すぎる」で弾かれます（実際に一度そうなり、
  `test_a_job_does_not_crowd_itself_out` はその回帰テストです）。
- **枠はランダム。** 毎日9:00/13:00/19:00のような固定パターンは、それ自体が自動化の指紋です。
  `next_slot` はジッター付きで前進しながら最初に全条件を満たす時刻を返します。
- **日次カウントの「日」はローカルタイムゾーンの暦日。** DBはUTC保存なので、
  ここを間違えると上限が日本時間の9時にリセットされます。

## 3.5 guard/policy.py — 法務・規約チェック

**責務**: 人間のレビュー時間を「判断が必要なもの」に集中させるため、明らかな地雷を先に落とす。

```python
check(item, policy_config, platform_config=None) -> PolicyReport
ensure_ai_disclosure(item, platform_config) -> bool   # 不足していれば追記
has_ai_disclosure(item, platform_config) -> bool
```

**検査項目**

| ルール | 深刻度 | 内容 |
|--------|--------|------|
| `banned_term` / `banned_pattern` | blocking | 設定した禁止語・正規表現 |
| `real_person` / `trademark` | blocking | 実在人物名・商標 |
| `ip_risk` | blocking | 「in the style of 〜」「ジブリ風」等の模倣表現、著名IP、ロゴ |
| `unsupported_claim` | blocking | 「絶対に稼げる」「〇〇が治る」等の保証表現（日英） |
| `affiliate_disclosure` | blocking | アフィリエイトリンクがあるのにPR表記がない |
| `ai_disclosure` | blocking | AI開示が必要なプラットフォームで開示がない |
| `link_density` / `hashtag_stuffing` | warning | スパム的な見た目 |

**設計判断**

- **`negative_prompt` は検査対象外。** ストック用プロンプトの `negative_prompt` には
  「no logo, no celebrity, no real person」と書きます。ここを検査すると、
  **最も安全なプロンプトほどブロックされます**。逆に `quality` 側で
  「negative_prompt にこれらの除外語が入っているか」を必須チェックにしています。
- **AI開示は文言一致ではなく表現パターンで判定。** 設定文と一字一句違うだけで
  ブロックするのは脆すぎます。「AI生成」「generated with ai」等のパターンのいずれかで合格。
- **AI開示は自動付与する。** 開示は創作ではなく機械的な要件なので、
  `ensure_ai_disclosure` が不足時に追記します。そのうえで `check` が結果を検証します
  （付与したことを信頼するのではなく、検証する）。

**拡張方法**: 語句の追加は `config/policy/*.yaml`。構造的なルールの追加は
`_INHERENT_RISK_PATTERNS` / `_CLAIM_PATTERNS` にタプルを足すだけです。

## 3.6 guard/quality.py — 品質と重複検知

**責務**: 「テンプレの使い回し」を検出する。これが量産とスパムの境界線です。

```python
check(item, quality_config, conn=None) -> QualityReport
similarity(a, b) -> float      # 文字4-gram の Jaccard 係数
normalize(text) -> str
```

**重複検知の仕組み**

1. 正規化：NFKC → 小文字化 → 記号と空白を除去
   （全角/半角・大小文字・句読点の違いは「内容の違い」ではないため）
2. 文字4-gramの集合を作る（日本語は分かち書きが不要なのでこの方式が有効）
3. 同一チャンネルの直近N件（既定200件）に対して Jaccard 係数を計算
4. 最大値が閾値（既定0.75）以上ならブロック

**設計判断**

- **重複検知はコーパス単位でしか見えない。** 1件ずつ見ている人間には絶対に気づけません。
  自動化する価値が最も高いチェックです。
- **チャンネルをまたいでは比較しない。** note記事とX投稿が似ているのは正常です。
- **文字数の上下限はチャンネル別。** X投稿280字、note記事800字以上など。
- **生成失敗の痕跡を検出。** 「As an AI language model」「[insert」「lorem ipsum」等が
  残っていたら即ブロックです。これが公開されるのが最も恥ずかしい事故です。
- **`fatal` と `warn` を区別。** キーワードが少ない等は警告に留め、人間の判断に委ねます。

## 3.7 guard/anomaly.py — 異常検知

**責務**: アカウントが制限される「前」に出る4つの兆候を監視する。

| 検知器 | 判定 | 自動停止 |
|--------|------|---------|
| `consecutive_failures` | 連続失敗が閾値以上 | **する**（設定で無効化可） |
| `platform_warning` | 応答に「suspend」「違反」「凍結」等が含まれる | **する** |
| `reach_drop` | 当日のリーチ < 直近中央値 × 40% | しない（通知のみ） |
| `quota_pressure` | 日次上限の80%到達 | しない（通知のみ） |

**設計判断**

- **中央値であって平均値ではない。** 1本バズると平均が跳ね上がり、
  その後の正常な日が全部「急減」に見えます。
- **リーチ急減では自動停止しない。** リーチは曜日・季節・話題で普通に半減します。
  ノイズの多い信号で自動停止するのは、それ自体が障害です。人間に判断させます。
- **連続失敗と警告文言は自動停止する。** これらは誤検知のコストより見逃しのコストが高い。
- **`defer`（枠がないだけ）は失敗にカウントしない。** レートリミットが正しく働いている状態で
  緊急停止が誤発火するのを防ぎます。

## 3.8 generators/ — 生成

### llm.py — プロバイダ抽象化

| プロバイダ | 用途 |
|-----------|------|
| `mock` | **既定**。オフライン・シード付き。鍵なし・課金なしで全経路をテストできる |
| `claude_cli` | ローカルの `claude` バイナリを headless で叩く |
| `anthropic` | Messages API を urllib で直接叩く（SDK不要） |

全プロバイダが**パースされたJSON**を返します。自由形式の文章は機械的にチェックできず、
ガードレールは離散的なフィールド（title / body / keywords）を必要とするためです。

### diversity.py — 多様性制御

theme × angle × tone の3軸で組合せを選びます。直近で使った組合せは除外し、
使用頻度の高いテーマ・切り口にはペナルティを課したうえでランダムに並べます。

> モデルに「毎回違う書き方で」と頼んでも、独立した呼び出しは同じ平均に回帰します。
> 多様性はプロンプトではなく**選択の側**で作る必要があります。

### service.py — 生成サービス

- **`approved` を書けない。** 最良の結果が `pending_review`、最悪が `blocked` です。
- **背圧制御。** 承認待ちが `max_pending_per_channel`（既定30件）に達したら生成を止めます。
  未レビューのキューが無限に伸びると、「人間が全部承認する」運用は事実上の
  ゴム印に変わります。キューの深さは安全装置です。
- **判定根拠を一緒に保存。** レビュー画面で「なぜ弾かれたか」が見えます。

## 3.9 approval/service.py — 承認ゲート

**責務**: `approved` に遷移させられる唯一の場所。

```python
queue(conn, status=, platform=, channel=) -> list[ContentItem]
approve(conn, settings, ref, *, actor, note="", force=False) -> Decision
reject / request_revision / edit / bulk_approve
```

**2つのルールがこのゲートに実効性を与えています。**

1. **承認時に再チェックする。** 生成時ではなく承認時点の本文に対してガードレールを再実行します。
   生成後の編集が、編集前にしか走っていないチェックをすり抜けることを防ぎます。
2. **上書きは明示的で、記録が残る。** ブロックされたものを承認するには
   `--force` と**書面の理由**の両方が必要です。監査ログには `approve_override` として
   理由付きで記録され、WARNINGレベルで残ります。黙ってブロックが解除されることはありません。

**その他**
- `bulk_approve` は決して force しません。一括承認は「問題のないものをまとめて通す」ためのもので、
  問題のあるものは必ず1件ずつ判断させます。
- 編集は承認を引き継ぎません（`pending_review` に戻る）。
- 却下すると、予約済みのジョブも同じトランザクションでキャンセルされます。

## 3.10 scheduler/planner.py — 予約と実行

```python
plan(conn, settings, limit=, platform=) -> PlanResult      # 承認済み → 枠を割当
run_due(conn, settings, notifier, now=) -> list[RunOutcome]  # 枠が来たジョブを実行
mark_published(conn, ref, external_url=)                   # 手動投稿の記録
```

**設計判断**

- **予約と実行を分離。** 予約時点で真だったことは実行時点で偽かもしれません
  （停止された、枠が埋まった、却下された）。`run_due` は予約時の判断を
  **ヒントとして扱い、許可としては扱いません**。
- **`Refusal(reason, kind)` で block と defer を区別。**（詳細は `01-architecture.md` 1.4）
- **`manual` 公開は「公開済」にしない。** `stages_for_human = True` のパブリッシャーは
  ファイルを書いただけで、何も投稿していません。項目は `staged`（手動投稿待ち）に入り、
  人間が `mark_published` で確定するまでそこに残ります。ここを「公開済」にしてしまうと、
  ダッシュボードが出ていないものを出たと言い、**既定の運用モードに作業リストが存在しなく
  なります**（`publisher: manual` が既定なので、これは主要な運用経路です）。
- **ただし投稿枠は staged の時点で消費します。** `db.published_timestamps` は `done` と
  `staged` の両方を数えます。確認待ちだからと枠を解放すると、次の実行が同じ枠に重ねて
  予約します。枠を多く数えて失うのは1投稿、少なく数えて失うのはアカウントです。

## 3.11 publishers/ — 公開

```python
class Publisher(Protocol):
    name: str
    performs_network_io: bool
    def publish(self, item) -> PublishResult: ...
```

**リトライ方針**（`base.py:with_retry`）

| 例外 | 挙動 |
|------|------|
| `TransientError` | 指数バックオフ + ジッターで再試行（ネットワーク・5xx・429） |
| `PublishError` | **再試行しない**。拒否された投稿は再投稿しても拒否される。拒否後に叩き続けるのは、軽い警告を本格的な凍結に変える最短ルート |

**`registry.py` の役割**: `dry_run` の適用を1箇所に集約しています。
ネットワークに触れるアダプタは無条件で `DryRunPublisher` に差し替わるので、
アダプタ側が `dry_run` のチェックを忘れても迂回できません。
アダプタは `ADAPTERS` に明示登録されたものだけが到達可能です。

## 3.12 revenue/ — 収益

**設計判断**: 全ソースをCSV取込または手入力にしています。これは機能の欠落ではなく判断です。

> A8.net にはアフィリエイト成果の公開APIがなく、note にも販売APIがありません。
> ログイン後の管理画面をスクレイピングすれば数字は取れますが、それは
> **ダッシュボードを埋めるためにアカウントを危険に晒す**取引です。本システムが避けるべきものです。

週に2分のCSVダウンロードで、アカウントリスクはゼロです。
正規APIがあるソース（YouTube Analytics 等）は後からアダプタを足せます。

**取込の実際**: 日本語列名（`日付` `報酬額` `件数`）、Shift-JIS、`1,234円` 形式、
複数の日付書式に対応。`(date, source, account, note)` がユニークなので、
同じCSVを何度取り込んでも二重計上しません。壊れた行はスキップして報告し、取込全体は失敗しません。

**レポート**: テキストのASCIIバーチャート。Discordに貼れて、メールで送れて、
スマホで読めます。画像だとこのどれもできません。
収益が1ソースに70%以上集中していると警告を出します（要件2.4の分散リスク）。

## 3.13 notify/notifier.py — 通知

Discord / Slack の Incoming Webhook は単なる HTTPS POST なので `urllib` で十分です。

**設計判断**: 送信失敗は**絶対に呼び出し元を落としません**。全て握り潰して bool で返します。
アラートの失敗がパブリッシャーをクラッシュさせたら、小さな問題が障害になります。

## 3.14 webui/ — 承認UI（任意）

スマホアプリの形をしたサーバサイドレンダリングのHTML。JSフレームワークもビルド工程もありません。
目的は「スマホで数分で承認キューを片付ける」ことで、この規模でSPAにすると
ツールチェーンとデプロイの面倒だけが増えます。

```
webui/
├── theme.py        デザイントークンとCSS（配色・タイポ・コンポーネント）
├── components.py   アプリシェル、タブバー、バッジ、カード、チャート
├── views.py        5つの画面 + レポート + 設定
└── app.py          ルーティングと操作（承認・却下・修正依頼・停止）
```

### 5つの画面

| タブ | 画面 | 用途 |
|------|------|------|
| タスク | **リスト** | 既定。状態別にグループ化したカード一覧。日常の承認作業 |
| タスク | **フロー** | パイプラインのどこに何件あるかを図で見る。作業画面ではない |
| タスク | **スワイプ** | 1件ずつ全文表示。溜まったキューを一気に捌く |
| タスク | **対話** | 会話形式。キューが短いとき、文脈込みで読みたいとき |
| レポート | **ダッシュボード** | 統計タイル・承認待ち・収益推移・収益源別・カテゴリー別件数 |
| 設定 | **設定** | 投稿枠の消化・緊急停止・設定値の確認 |

**5つとも同じ `approval.service` を呼びます。** 画面はプレゼンテーションであって
ポリシーではないので、どの画面から承認しても、ガードレールのチェックも監査記録も
上書きのルールも変わりません。

### 画面ごとに変えている点（安全側の判断）

- **スワイプにブロック項目を入れていません。** ガードレールが拒否したものに
  ワンタップ承認を与えるのは、まさに間違った操作性です。別枠で件数だけ示し、
  理由が画面に出る詳細画面へ誘導します。速さは定型の項目のためのものです。
- **リストのブロックカードには承認ボタンがありません。**「理由を確認」と「却下」だけです。
- **詳細画面の上書き承認は、赤い破線で囲った最も目立たない位置**に置いています
  （3.9 の上書きルールと対応）。

### 可視化

- **日次の収益推移** — 単系列のエリアチャート。単系列なので凡例は不要（見出しが系列名）。
  カテゴリカルではなくシーケンシャルな青を使っています。仕事は「時間に沿った量の変化」で
  あって「識別」ではないからです。
- **収益源別** — 単色の横バー。値を必ず数字で併記しているので、読み取りが色に依存しません。
- **状態の色** — good / warning / critical の3色を状態専用に予約し、系列色と分けています。
  系列色が状態を装うことがないようにするためです。色は必ずラベルと併用します。
- 配色は実測しています（白文字 on ヘッダー6.6:1、承認ボタン5.5:1、却下ボタン6.0:1）。
  ダークモードは自動反転ではなく、ダーク面に対して選び直した値です。

### セキュリティ

**認証はありません。** `127.0.0.1` にバインドし、環境変数
`AIWORKER_ALLOW_PUBLIC_BIND=1` がない限り公開インターフェースへのバインドを拒否します。
ネットワーク上の誰でも承認できるキューは、承認ゲートではないからです。
リモートから使う場合はSSHトンネル（`ssh -L 8787:127.0.0.1:8787 <host>`）を使ってください。
